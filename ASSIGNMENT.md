## 1. The feature

| Rule | Behaviour | Where |
|---|---|---|
| R1 | A Manager approves alone up to 50,000.00 (inclusive) | `ApprovalLimits.LimitFor`, `ApprovalService.Approve` |
| R2 | A Director approves alone up to 500,000.00 (inclusive) | same |
| R3 | Above 500,000.00: first approval (Manager or Director) keeps the invoice pending and records `FirstApprovedBy`/`FirstApprovedAt`; the second must be a Director | `ApprovalService.Approve` |
| R4 | The same user never counts twice: names trimmed and compared ordinal ignore-case with the stored first approver | same |
| R5 | A denial throws `ApprovalDeniedException` → HTTP 409 `{ "error": "<reason>" }`, shown verbatim in the UI; **every check runs before any field changes and before the repository is called** | `ApprovalService`, `ApiControllerBase`, `wwwroot/app.js` |

Roles and demo users: `demo.manager` (Manager), `demo.director` and `demo.director2` (Director), `demo.admin` (Admin: rejects and deletes, cannot approve), password `ChangeMe123!`. Seeded pending invoices `INV-1006` (75,000) and `INV-1007` (750,000). Decisions and the full test matrix: `docs/decisions/DECISIONS.md`.

## 3. Context that earns its place (`AGENTS.md`)

`AGENTS.md` tells an agent arriving cold the approval rules with inclusive boundaries, the check order, the canonical messages, the layering (Domain decides, Api maps, UI shows), every command, the testing and review expectations, and — specifically — **where agents usually get R4 and R5 wrong** (mutate-then-throw, case-sensitive identity, checking only the second approver's role). That table is why the denial tests snapshot every field and count repository saves, and the later reviews and mutation runs confirmed those exact mistakes are caught. All sub-agents were briefed from `AGENTS.md`, the skills and the decisions, and produced consistent code, tests, spec and UI text (one message set, `docs/decisions/DECISIONS.md` D-31).

## 6. Tests

- **Unit (xUnit): 114 tests, all green** — `ApprovalServiceTests`, `ApprovalLimitsTests`, `ApprovalDeniedExceptionTests`, `InvoiceTests`, `DiscountCalculatorTests` (labelled as outside the feature).
- **Every rule has positive and negative tests**, boundaries on both sides (49,999.99 / 50,000.00 / 50,000.01 / 500,000.00 / 500,000.01).
- **The two negative rules:**
  - **R4** — same user by exact name, other letter case, surrounding spaces, a tab, a stored name in another case, under the Turkish culture; a Manager repeating their own first approval gets the same-user reason; a second Director whose name contains the first one's name is still allowed.
  - **R5** — every denial asserts the exact exception type, the full reason, that all six decision fields are unchanged (also when they held earlier values) and that the repository was not called (`UpdateCalls == 0`).
- **Review of every generated test:** `docs/evidence/test-review-step1.md` and `test-review-step2.md` — 8 gaps found by the adversarial reviewer, each fixed and proven by applying the bug by hand and watching the new test fail.
- **End to end (Playwright):** `e2e/tests/approval-limits.spec.ts` — a Manager creates and submits a 60,000 invoice, tries to approve it, sees the exact reason, and after a page reload the invoice is still pending in the UI and through the API. `docs/evidence/e2e-run.txt` (incl. a proof that a wrong expectation fails).

Notable: the first after-run reported 100 % for `ApprovalService` but its log showed Stryker's **Safe Mode had removed all 39 mutants of `Approve`** (one mutant did not compile). Stryker does not mutate the comparison argument, the `Trim()` calls or plain assignments; those are covered by the hand-applied mutants in the test reviews. ## 9. AI interaction log and human oversight

- `logs/ai-interactions.jsonl` — one structured record per interaction (tool, model, agent type and mode, request, skills, sub-agents, MCP tools, tools, verification result, human decision, status, files, commit), generated by the hooks and rebuilt from the Claude Code transcript; schema in `logs/README.md`.
- `logs/AI_INTERACTION_LOG.md` — readable summary per stage; `logs/HUMAN_OVERSIGHT.md` — the participant's decisions.
- Human prompts are paraphrased from the real session (the participant's own wording, status checks and log-format discussions are omitted at their request; setup turns are one line). Every paraphrase is tied to the timestamp of the real message — the rebuild refuses entries without one and fails if any fragment of a real message remains (`logs/curation.json`). Agent actions, tools, verifications and commits are recorded as they happened.
- Oversight in practice: plan approved before code; decisions on tooling, identity, delivery order and the mutation target; every sub-agent output re-read and re-run by the main agent; 8 test-review findings and 15 PR-review findings judged one by one.

## 11. Known limitations (deferred, with follow-ups)

- **Concurrency (RA-01):** two simultaneous approvals on the in-memory store are not serialised; follow-up is optimistic concurrency when real persistence is added.
- **CI (RC-07):** CI runs build and unit tests; the e2e test and the mutation score are local gates for now.
- **Guard (RC-06):** `guard.js` is best-effort defence in depth; permission deny rules are a repository-owner decision.
